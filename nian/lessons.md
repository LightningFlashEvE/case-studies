# 踩坑总结

## 1. 服务错误和回答格式错误需要分开定位

服务端返回 HTTP 错误，与请求成功后内容不能解析，是两条不同故障路径。只显示通用错误码会让用户把不同问题当成同一次故障。诊断至少需要记录状态、阶段和耗时，同时避免把密钥或完整私人回答写入日志。

## 2. 结构化工具也需要校验和修复

声明工具并不能保证每次都收到有效工具参数。模型可能返回普通段落，或者在修复格式后仍违反字段范围。格式修复与内容校验如果共用一次重试额度，前者会耗尽后者的机会。更合理的处理是分别设置有界额度，并在需要提交答案时明确选择完成工具；修复后的出处仍要重新校验。

## 3. 来源标识可能占用大量上下文

大量重复的长标识会扩大笔记合并请求。请求内部可以使用短别名，但存储前必须严格还原并检查来源。不能为了减少文本量丢失追溯关系。

## 4. 通用默认上限可能误伤正常数据

结构校验器的默认数组上限，可能意外限制包含许多来源的合并结果。应按具体字段设计约束，并用超过默认上限的真实形态回归测试验证。放宽长度限制不能替代来源合法性检查。

## 5. 全库概览不等于每次全文扫描

用户问整体进展时，先读取已有浓缩资料通常更符合需求。精确数字、计划变更和原话仍需要下钻。优化之前先检查调用路径，否则更换向量实现也可能无法消除重复模型调用带来的等待。

## 6. 没有摘要不代表录音没有价值

任务未触发、服务失败和内容确实无意义都会导致“没有笔记”，但只有最后一种可能成为清理依据。清理应沿来源关系处理音频、文本和派生索引，同时保护人工修改及有效引用。

## 7. 本地检查和实机结果是两类证据

单元测试验证可重现的行为边界；实机复测检查实际供应商、设备和数据规模下的结果。一次成功不能证明错误永不发生。发布时应区分已通过的检查、已完成的实机流程和仍未覆盖的长期场景。
