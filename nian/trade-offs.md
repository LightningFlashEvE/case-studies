# 技术选型：选择依据与代价

下表讨论本案例的工程取舍，不是供应商榜单；没有把未经统一测试的模型质量或延迟写成结论。

| 决策 | 方案一 | 方案二 | 本案例采用的方向与代价 |
|---|---|---|---|
| 数据落点 | 直接依赖云端处理 | 先在本机持久化 | 优先本机保存，提升断网恢复能力；需要处理存储、备份和设备损坏风险 |
| 转写 | 本地推理 | 云端接口 | 保留按配置选择的能力；本地消耗设备资源，云端受网络、费用与数据传输约束 |
| 应用层 | 原生平台分别开发 | Flutter 配合原生采集桥接 | 复用界面与业务逻辑；锁屏采集、设备连接仍需要原生工程能力 |
| 元数据 | 文件分散管理 | 本地关系型数据库 | 用数据库管理来源、任务和修订；音频文件与数据库之间仍需一致性恢复 |
| 检索 | 仅关键词 | 关键词加本地语义候选 | 兼顾原词与同义表达；需要处理模型资源、候选筛选和索引重建 |
| 广泛回顾 | 每次读取全部原文 | 优先读取已有笔记 | 降低重复读取；笔记不完整或问题需要细节时必须回查原文 |
| 模型交互 | 自由文本后解析 | 结构化工具输出 | 优先结构化工具；仍需防范格式错误、无效参数和不存在的出处 |
| 容错 | 无限制自动重试 | 有界重试与明确失败 | 控制费用和等待时间；格式修复与内容校验应分别计数 |

## 如何评估后续替换

模型或检索方案替换应使用同一组虚构或获准使用的测试样本，分别记录准确性、来源有效性、端到端耗时、设备资源和请求成本。冷启动与已有缓存要分开测量；不能把少量实机检查当作长期稳定性证明。
